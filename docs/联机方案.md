# 联机功能开发方案

> 目标形态：**合作爬塔**（2-4 人同爬一座塔，共享层数，各自携带各自的装备与战利品）
> 权威模型：**主机权威 + P2P**（房主客户端裁决局内战斗，服务端管账号与存档）
> 网络方案：**Unity Netcode for GameObjects (NGO)**
> 后端方案：**自建服务器**（账号 / 云存档 / 中继 / 房间）
> 服务端语言：**Go**
> 部署环境：**先本地验证，验证通过后再上云**
> **范围说明：本期不做防作弊**（见 2.5）
> 本文档为评审稿，评审通过后再进入实施。

## 一、当前项目架构审查

### 1.1 程序集结构

| 程序集 | 职责 | 依赖 |
|---|---|---|
| `Inventory` | 纯数据层：物品 / 容器 / 存档 / 服务 | 无 |
| `BattleHUD` | 局内 UI | Inventory, TMP |
| `Gameplay` | 战斗逻辑 | BattleHUD, Inventory |
| `Assembly-CSharp`（UI/MainMenu、Editor） | 主菜单 UI、编辑器工具 | 全部 |

分层是单向的，`Inventory` 不依赖任何场景对象。这个结构对联机友好：数据层可以整体搬到服务端复用。

### 1.2 已有的「联机友好」设计（重要资产）

代码里已经埋了为联机预留的钩子，这是本次开发的最大优势：

| 位置 | 现有设计 | 联机价值 |
|---|---|---|
| `FloorGenerator` | 全部静态纯函数，接收 `System.Random` 而非 `UnityEngine.Random` | 权威随机可移到服务端，同种子可复现 |
| `LootPool.Roll(floor, System.Random)` | 同上 | 掉落掷点可服务端权威 |
| `LootDropper.HandleDied` | 注释已写明「联机化时改为主机权威调用」 | 掉落生成点已收敛 |
| `LootInteractor.TryPickup` | 注释已写明「将来接联机时只改这个方法内部」 | 拾取入口已收敛 |
| `PlayerWeaponSelector.Toggle` | 注释已写明「将来接联机时把 Toggle 改成发请求即可」 | 切武器入口已收敛 |
| `ModeTabSelector` | 单机 / 联机二选一 UI **已存在**，`ModeChanged` 事件已暴露 | 入口 UI 无需新建 |
| `GameSession` | 进程内单例，主菜单与战斗场景共享同一对象 | 单机语义清晰，联机需按玩家分实例 |

### 1.3 联机化的核心障碍

| 障碍 | 位置 | 说明 |
|---|---|---|
| **全局单例 `GameSession`** | `GameSession.cs` 静态字段 | 只能容纳一个玩家。多人必须改为「按 PlayerId 索引」 |
| **`FindObjectsOfType` 全局扫描** | `RifleShooter2D`、`LootInteractor`、`TowerRunManager`、`SpawnerSummoner2D`、`EnemyLaserProjectile2D` | 无法区分「我的敌人」与「别人的敌人」，性能随人数线性劣化 |
| **玩家硬编码单例** | `EnemyBrain2D.Awake` 里 `FindObjectOfType<PlayerMovement2D>()` | 敌人只会追第一个玩家 |
| **`PlayerHealth2D` 直接改 `GameSession.Loadout`** | `PlayerHealth2D.TakeDamage` 里 `GameSession.Loadout.NotifyChanged()` | 受击磨损直接写局外资产，联机下需服务端裁决 |
| **`Time.timeScale = 0` 暂停** | `PlayerDeathFlow2D`、`PortalConfirmPanelController` | 单人暂停语义，多人下会冻结所有人 |
| **`PlayerPrefs` 存档** | `PlayerSaveStore`、`CollectionStore`、`PlayerCurrency` | 本地存档，云存档需服务端权威 |
| **`System.Random` 无种子** | `TowerRunManager.Awake` 里 `new System.Random()` | 每台机器种子不同，房间布局 / 敌人 / 掉落全不一致 |

## 二、方案选型与关键决策

### 2.1 权威模型：主机权威 + P2P（决策项 D1，已定）

#### 2.1.1 什么是主机权威

**权威（Authority）= 谁说了算。** 每个游戏状态（玩家位置、血量、敌人位置、掉落物）都需要有人拍板。

**主机权威**：由其中一个玩家（房主）的客户端来拍板。

```
房主（Host）                    客户端（Client）
├─ 跑完整的游戏逻辑              ├─ 只跑本地输入
├─ 敌人 AI 在这里算              ├─ 把输入发给房主
├─ 伤害结算在这里做              ├─ 收到状态后插值显示
├─ 掉落掷点在这里做              └─ 不做任何决策
└─ 把结果广播给所有人
```

**关键**：房主既是玩家，又是「服务器」。他的客户端比其他客户端多干一份活。

#### 2.1.2 为什么会有 NAT 穿透问题

家用路由器（NAT 设备）会把内网地址（如 `192.168.1.100`）转换成公网地址，导致：

- **内网地址对外不可见**：主机告诉客户端「我在 `192.168.1.100:7777`」，客户端根本连不上。
- **路由器不会主动放行**：即使主机知道自己的公网 IP，路由器默认丢弃「未经请求」的外部连接。

**是否需要穿透，取决于权威模型：**

| 权威模型 | 连接拓扑 | 是否需要穿透 |
|---|---|---|
| **主机权威**（主机是玩家之一） | 玩家 ←→ 玩家 | **需要** |
| **Dedicated Server**（战斗跑在服务器） | 玩家 → 服务器 ← 玩家 | **不需要**（双方都是主动外连） |

> 关键结论：**只要「主机是玩家之一」，就必须解决穿透。** 这是主机权威方案的固有成本。

#### 2.1.3 三条路线对比

| 路线 | 穿透需求 | 服务器带宽成本 | 战斗逻辑改造 | 服务端复杂度 |
|---|---|---|---|---|
| **A. 主机权威 + P2P** ← **已选** | 需要（STUN/TURN） | 低（仅信令 + 存档） | 小 | 低 |
| **B. 主机权威 + 中继转发** | 不需要 | **高**（战斗流量全过服务器） | 小 | 低 |
| **C. Dedicated Server** | 不需要 | 中（只同步状态，流量反而更小） | **极大** | 高 |

> 注意路线 B：虽然绕过了穿透，但每个房间的战斗流量都要过服务器，带宽成本随在线人数线性增长。而路线 C 只同步状态，流量反而更小。

#### 2.1.4 选路线 A 的理由

1. 本项目是 **PvE 合作爬塔**，无 PvP，主机作弊的收益极低（只能给自己刷装备，不影响他人体验）。
2. 代码里所有「权威点」已收敛到少数几个方法（掉落、拾取、切武器、层生成），改造成本可控。
3. `FloorGenerator` / `LootPool` 已是 `System.Random` 纯函数，**主机生成种子 → 广播种子 → 各端本地复现**，无需同步房间布局的每个对象。
4. 路线 C 需要把 Unity 2D 物理与 AI 搬到服务端，成本极高，与「合作 PvE」的收益不匹配。

**权威分层**：

| 层 | 权威方 | 说明 |
|---|---|---|
| 局内战斗（移动、伤害、掉落、拾取） | **主机** | 保持现有 Unity 物理与 AI 逻辑，改造成本可控 |
| 局外资产（仓库、装备、货币、收藏） | **服务端** | 所有写入走服务端 API，服务端只做存储 |
| 撤离结算 | **客户端 → 服务端** | 客户端提交本局战利品清单，服务端直接落库（**本期不做校验**） |

> 这是**混合权威**模式，也是现代主流做法：局内战斗用主机权威（省服务器成本），局外资产用服务端权威（换设备能同步）。

> **本期不做防作弊**：服务端不校验战利品清单的合法性，客户端上报什么就存什么。详见 2.5。

#### 2.1.5 NAT 穿透方案

| 方案 | 说明 | 可行性 |
|---|---|---|
| 玩家直连（P2P） | 主机开端口，客户端直连 IP | 仅局域网可行。公网需玩家自己配端口映射，**不可接受** |
| **自建 STUN/TURN** | 用 STUN 打洞，失败时回退 TURN 中继 | **已选**。打洞成功时流量不过服务器，成本低 |
| 纯中继转发 | 所有流量经服务器转发 | 连通率 100%，但带宽成本高 |

**采用自建 STUN/TURN**（开源 coturn）。打洞成功率通常在 80-90%，失败时回退中继。

> **前置验证建议**：在投入后续开发前，先用 coturn 跑通「两个不同网络下的客户端互连」，确认打洞成功率可接受。这是路线 A 唯一可能卡住项目的技术点。

#### 2.1.6 后期升级到服务端权威的退路

若后期需要更强反作弊，架构上留了退路：

| 步骤 | 难度 | 说明 |
|---|---|---|
| 1. 把纯逻辑搬到 Go | **低** | `FloorGenerator` / `LootPool` / `EnemyBrain2D.ResolveState` 都是纯函数，可直接移植 |
| 2. 把伤害结算搬到服务端 | **中** | 客户端上报「我打中了谁」，服务端校验后结算 |
| 3. 把物理搬到服务端 | **高** | 用 Go 自写轻量 2D 物理，或改用 Unity Dedicated Server |

> **第一步和第二步就能挡住大部分作弊**，第三步（物理）才是真正的大工程。建议先做主机权威版本，验证玩法后再评估是否需要升级。

### 2.2 网络库：Unity Netcode for GameObjects

- Unity 官方方案，与现有 MonoBehaviour 架构融合度高。
- 支持 Host / Client 与 Dedicated Server 两种模式，后续可平滑升级到路线 C。
- 传输层用 `Unity Transport`，可自定义 Relay 指向自建 STUN/TURN。

### 2.3 后端服务：自建

> **详细设计见 [Go后端设计.md](./Go后端设计.md)**（模块划分、API 定义、数据表、部署架构）。
>
> **本期范围裁剪**：后端只做 **账号 + 房间 + 信令 + 中继**，**存档模块暂不做**（客户端继续用本地存档）。

| 组件 | 技术选型 | 职责 |
|---|---|---|
| **业务 API** | **Go**（`gin` / `echo`，或标准库 `net/http`） | 账号、存档、结算校验 |
| **数据库** | PostgreSQL + `pgx` | 玩家账号、局外资产、收藏、货币 |
| **数据访问** | `sqlc`（推荐）或 `GORM` | `sqlc` 从 SQL 生成类型安全代码，比 ORM 更可控 |
| **认证** | `golang-jwt/jwt` + `x/crypto/bcrypt` | JWT 签发校验、密码哈希 |
| **中继** | coturn（独立进程，开源 STUN/TURN） | NAT 穿透与流量中继；Go 侧只做信令 |
| **缓存** | Redis（可选） | 会话 Token、在线状态、速率限制 |
| **日志** | `zerolog` 或 `zap` | 结构化日志 |
| **部署** | Docker 多阶段构建 | 编译阶段 + 精简运行阶段 |

**自建相比 UGS 的差异**：

| 维度 | UGS | 自建 |
|---|---|---|
| 账号系统 | 现成 | 需自己实现（注册 / 登录 / 密码哈希 / Token） |
| 云存档 | 现成 | 需自己实现（表设计 + API + 冲突处理） |
| NAT 穿透 | 现成（Relay） | 需自建 STUN/TURN |
| 房间列表 | 现成（Lobby） | 需自己实现 |
| 运维 | 无 | 需自己承担（部署 / 监控 / 扩容 / 备份） |
| 可控性 | 受限于 UGS | **完全可控**，校验逻辑可任意定制 |
| 成本 | 按用量付费 | 服务器固定成本 + 带宽 |

### 2.4 服务端技术栈：Go（决策项 D2，已定）

#### 2.4.1 选 Go 的收益

| 收益 | 说明 |
|---|---|
| **部署极简** | 编译成单个二进制，无运行时依赖，Docker 镜像可小到 10MB 级 |
| **并发模型优秀** | goroutine + channel 天然适合「大量房间 + 长连接」场景 |
| **资源占用低** | 相比 .NET 运行时，常驻内存更低，适合小成本服务器 |
| **运维简单** | 无 GC 调优负担，无运行时版本管理 |

#### 2.4.2 选 Go 的代价

| 代价 | 说明 | 本期影响 |
|---|---|---|
| 无法复用 C# 游戏逻辑 | `FloorGenerator` / `LootPool` 等需用 Go 重写 | **无影响**——本期不做校验，服务端不需要这些逻辑 |
| 两套代码漂移风险 | 若服务端复算游戏逻辑，需保证与客户端一致 | **无影响**——同上 |

> **重要**：因为本期不做防作弊，Go 方案原本最大的代价（校验逻辑需重写）**在本期完全不存在**。服务端只做账号、存档、房间、信令，不涉及任何游戏逻辑。这是「不做防作弊」带来的最大收益。

### 2.5 范围说明：本期不做防作弊

#### 2.5.1 明确不做的事

| 不做的事 | 说明 |
|---|---|
| 战利品清单校验 | 客户端上报什么就存什么 |
| 掉落复算 | 服务端不复算「本层应该掉什么」 |
| 物品来源链校验 | 不追溯每件物品的来源 |
| 速率限制 | 不限制单位时间内的拾取 / 撤离次数 |
| 存档签名 | 存档不带服务端签名 |

#### 2.5.2 服务端职责（收缩为纯存储 + 信令）

```
服务端 = 账号 + 存档 + 中继 + 房间
```

服务端是一个**纯粹的存储与信令服务**，不参与任何游戏逻辑判断。

#### 2.5.3 仍然保留的两项（非防作弊，属基础健壮性）

| 项 | 为什么保留 |
|---|---|
| **存档版本号** | 客户端版本升级后存档格式可能变化，需要版本号做迁移。与防作弊无关 |
| **基础输入校验** | 如「仓库格号必须在 0-71 之间」。这不是防作弊，是防止**客户端 bug 导致服务端崩溃或数据损坏** |

#### 2.5.4 后续如需加强防作弊

架构上已为此留好退路，但**本期明确不做以下两项预留**（已决策）：

| 项 | 本期决策 | 后期补的代价 |
|---|---|---|
| **换掉 `System.Random`** | **暂不换** | **高**——需回头改客户端 `FloorGenerator` / `LootPool` 的参数类型，并回归验证单机体验不变 |
| **拾取时记录物品来源** | **暂不加** | **中**——改动本身不难，但**历史数据断层**无法弥补（老玩家的物品无来源记录） |

**后期补防作弊的难度分级**：

| 防作弊手段 | 后期补的难度 | 说明 |
|---|---|---|
| 速率限制 | **低** | 纯服务端新增，客户端零改动 |
| 存档签名 | **低** | 服务端加签、客户端加验签，改动局部 |
| 层数时间约束 | **低** | 纯服务端逻辑 |
| 物品来源链 | **中** | 需客户端新增上报 + 服务端流水表；有历史数据断层 |
| 掉落复算（PRNG 未换） | **高** | 需返工客户端 PRNG，并回归单机体验 |
| 掉落复算（PRNG 已换） | **低** | 纯服务端加逻辑 |
| 完整战斗复算 | **极高** | 需把战斗逻辑搬到服务端，等于重做架构 |

> **关键结论**：除「掉落复算」外，其余防作弊手段后期补都是**纯服务端增量**，不影响已完成的客户端模块。因此本期不做防作弊**不会显著加大后期难度**，代价集中在「掉落复算」这一条路径上。

### 2.6 战利品归属：先到先得（决策项 D3，已定）

**规则**：地面掉落物是**全局共享**的，谁先拾取归谁。一件掉落物被任一玩家拾取后立即从场景移除，其他玩家无法再拾取。

**实现要点**：

| 项 | 做法 |
|---|---|
| 掉落物生成 | 主机权威：主机生成掉落物并同步到所有客户端 |
| 拾取请求 | 客户端发「我要拾取 X」→ 主机校验（距离、是否已被拾取）→ 主机裁决归属 |
| 归属结果 | 主机广播「X 归玩家 P」→ 各端从场景移除 X，仅 P 的 `RaidBag` 增加该物品 |
| 冲突处理 | 同一帧多人请求同一件：主机按**到达顺序**裁决，先到者得，后到者收到「已被拾取」失败回执 |

**注意**：因为不做防作弊，主机裁决结果即为最终结果，客户端不校验。但**拾取必须走主机**，否则各端本地各自拾取会导致物品重复（同一件物品被两个玩家同时拿走）。

**与现有代码的关系**：`LootInteractor` / `LootScan` 目前是本地直接拾取，阶段 3 需改为「发请求 → 等主机裁决」。

### 2.7 死亡处理：观战 + 可复活（决策项 D4，已定）

**规则**：玩家死亡后**不退出本局**，转为观战状态，可被队友复活。

| 状态 | 行为 |
|---|---|
| 死亡瞬间 | 玩家角色倒地（保留尸体或墓碑），该玩家进入**观战模式** |
| 观战模式 | 相机可自由跟随存活队友；不能操作角色、不能拾取、不能攻击 |
| 复活方式 | 队友在尸体旁交互（长按 / 消耗道具）→ 玩家以一定血量复活 |
| 复活后 | 恢复操作，装备与携带格**保持死亡时的状态**（不清空） |
| 全员死亡 | 本局失败，走 `AbandonRaid` 流程（清空携带 + 清空装备槽） |

**关键设计问题（待实现时确认）**：

- 复活是否需要消耗品 / 是否有次数限制
- 复活后的血量比例（建议 30%–50%）
- 尸体是否会被敌人攻击 / 是否有存在时限

**与现有代码的关系**：`PlayerDeathFlow2D` 目前是「死亡 → 结算面板 → 回主菜单」。阶段 3 需新增 `multiplayerMode` 分支：联机时死亡不触发结算，改为进入观战 + 广播死亡状态。该开关已在阶段 0 的 0.4 步骤中预留。

### 2.8 撤离粒度：全员一起撤离（决策项 D5，已定）

**规则**：**所有存活玩家必须同时站在同一个传送阵内**，才能触发撤离。任一玩家不在阵内，撤离不触发。

| 场景 | 行为 |
|---|---|
| 部分玩家在阵内 | 显示「等待队友」提示，不触发撤离 |
| 全员在阵内 | 触发撤离倒计时（建议 3 秒，给反悔窗口）→ 倒计时结束仍在阵内则撤离成功 |
| 倒计时中有人离开 | 倒计时取消，回到「等待队友」 |
| 有玩家处于死亡观战状态 | **不阻塞撤离**（死亡玩家不参与「全员」判定），存活玩家全部在阵内即可撤离 |

**实现要点**：

- 传送阵触发判定由**主机**执行（主机知道所有玩家位置）
- 主机检测「存活玩家集合 ⊆ 阵内玩家集合」→ 广播撤离开始
- 撤离成功后，各玩家的携带格分别并入各自仓库（`ExtractToLoadout` 按玩家逐个执行）

**与现有代码的关系**：`FloorPortal2D` / `PortalConfirmPanelController` 目前是单人触发。阶段 3 需改为主机聚合判定。

### 2.9 保留离线单机模式（决策项 D6，已定）

**规则**：**单机模式完整保留**，不依赖网络。玩家可以不登录、不联网，直接开始爬塔。

| 模式 | 入口 | 存档 | 战斗权威 |
|---|---|---|---|
| **单机模式** | 主菜单「开始游戏」 | 本地存档（现有 `PlayerSaveStore`） | 本地（现有逻辑，零改动） |
| **联机模式** | 主菜单「联机」→ 登录 → 建房 / 加入 | 云端存档（登录后同步） | 主机权威 |

**实现约束（重要）**：

1. **单机路径不得引入任何网络依赖**：`GameSession`、`TowerRunManager`、`PlayerMovement2D` 等核心逻辑在单机下走原有分支，不经过 NGO。
2. **联机是叠加层，不是替换**：所有联机改动通过**开关 / 接口实现**接入，单机时开关关闭、走原路径。
3. **存档合并策略**：离线期间用本地存档；登录后以云端为准做一次合并（具体合并规则在阶段 1 确定）。
4. **回归要求**：每个联机阶段完成后，必须回归验证单机全流程（主菜单 → 出征 → 爬塔 → 撤离 / 死亡）行为不变。

> 这条决策是**整个联机开发的硬约束**：任何一步改动如果破坏了单机可玩性，都视为不合格。

### 阶段 3：权威逻辑迁移

**目标**：所有影响游戏状态的决策由主机裁决，保证各客户端状态一致。

| 任务 | 权威点 | 改造方式 |
|---|---|---|
| 3.1 层生成 | `TowerRunManager.BuildFloor` | 主机生成 `seed` → `ClientRpc` 广播 → 各端 `new System.Random(seed)` 本地复现 |
| 3.2 敌人 | `SpawnEnemies` | 主机 `Spawn` 敌人 `NetworkObject`；敌人 AI 只在主机跑（`IsServer` 判断） |
| 3.3 伤害 | `IDamageable.TakeDamage` | 改为 `ServerRpc` 请求 → 主机结算 → `ClientRpc` 广播血量 |
| 3.4 掉落 | `LootDropper.HandleDied` | 主机掷点 + 生成 `NetworkObject` 掉落物 |
| 3.5 拾取（先到先得） | `LootInteractor.TryPickup` | `ServerRpc` 请求 → 主机校验距离 / 背包容量 / **是否已被拾取** → 按到达顺序裁决归属 → 广播「归玩家 P」并销毁掉落物 |
| 3.6 换层 | `TowerRunManager.ExecutePortal` | 主机裁决，广播层数变更 |
| 3.7 死亡（观战 + 可复活） | `PlayerDeathFlow2D` | 联机分支：死亡不结算，转观战 + 广播死亡状态；新增队友复活交互（`ServerRpc` → 主机校验 → 广播复活） |
| 3.8 撤离（全员一起） | `FloorPortal2D` / `PortalConfirmPanelController` | 主机聚合判定「存活玩家 ⊆ 阵内玩家」→ 广播撤离倒计时 → 倒计时结束仍在阵内则各玩家 `ExtractToLoadout` 逐个执行 |
| 3.9 撤离结算 | `GameSession.ExtractRaid` | 客户端提交战利品清单 → 服务端直接落库 |

> **注意**：3.3 / 3.5 的「主机校验」是**游戏逻辑校验**（如「距离够不够近」「背包满没满」「是否已被别人拾取」），不是防作弊校验。这些校验是保证游戏正确性所必需的，与 2.5 节「不做防作弊」不冲突。

**验收**：各客户端看到的敌人、掉落、层数一致；拾取无重复归属；全员撤离判定正确；死亡玩家可被复活；主机断线时 Client 有明确提示。

## 四、设计决策（已确认）

以下问题已确认，实现细节见第二章对应小节。

### 4.1 战利品归属：先到先得

掉落物全局共享，谁先拾取归谁。拾取必须走主机裁决，避免同一件物品被多人同时拿走。详见 2.6。

### 4.2 死亡后的处理：观战 + 可复活

死亡不退出本局，转为观战状态，队友可复活。全员死亡才判定本局失败。详见 2.7。

### 4.3 撤离的粒度：全员一起撤离

所有存活玩家须同时站在同一个传送阵内才触发撤离；死亡观战玩家不阻塞撤离。详见 2.8。

### 4.4 层数推进：共享层数

全员在同一层，清空后一起进下一层。与现有 `TowerRunState` 最契合，无需为每人维护独立状态。

### 4.5 离线模式：保留

单机模式完整保留，零网络依赖；联机作为叠加层接入。详见 2.9。

## 五、工作量与风险

### 5.1 阶段依赖

```
阶段 0（解耦）──┬──> 阶段 2（传输层）──> 阶段 3（权威迁移）──> 阶段 4（体验）
                │
                └──> 阶段 1（自建后端）──> 1A 本地验证 ──> 1B 上云
```

阶段 0 是硬前置，必须最先做。阶段 1 与阶段 2 可并行。

### 5.2 工作量结构（相对占比）

```
阶段 0 架构解耦        ████████████████  ~40%   ← 硬前置，无可见产出
阶段 1 自建后端        ████████          ~20%   ← 含 1A 本地验证 + 1B 上云
阶段 2 传输层接入      ██████            ~15%
阶段 3 权威迁移        ██████████        ~25%
阶段 4 体验完善        ██                ~5%    ← 按需
```

> **不做防作弊使阶段 1 从 ~30% 降到 ~20%**（服务端无需移植任何 C# 游戏逻辑），整体工作量相应减少。

### 5.3 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **NAT 打洞成功率不达标** | 路线 A 可能不可行，需回退路线 B（带宽成本高）或路线 C（改造极大） | **阶段 1A.7 前置验证**，先跑通再投入后续开发 |
| 阶段 0 触及核心战斗代码 | 可能引入单机回归 bug | 依赖现有 EditMode 测试；每步单独验证 |
| `FindObjectsOfType` 收敛不彻底 | 联机下出现「敌人追错人」「拾取到别人的掉落」 | 阶段 0.3 用 `WorldRegistry` 一次性替换，并加断言 |
| NGO 与现有 `Rigidbody2D.MovePosition` 移动方式冲突 | 位置同步抖动 | 本地玩家用 `NetworkTransform` 的 Client Authority，非本地玩家插值 |
| 存档上云后单机也依赖网络 | 离线不可玩 | 保留离线模式 + 登录后合并 |
| **自建服务运维成本** | 需长期投入（部署 / 监控 / 扩容 / 备份） | 先本地验证，确认方案可行再上云；容器化降低运维复杂度 |
| **无防作弊** | 玩家可改内存刷装备 | **本期明确接受**；架构已留退路（见 2.5.4），后续可增量加强 |

### 5.4 建议的实施顺序

1. **阶段 0 全部完成并回归单机**（这是唯一不可跳过的地基）
2. **阶段 1A.7 穿透验证**（用 coturn 跑通两个不同网络的客户端互连）—— **这是路线 A 的关卡，建议尽早验证**
3. **阶段 2 最小闭环**：两个客户端能连上、能互相看到移动
4. **阶段 1A 其余部分**：账号、存档、房间服务
5. **阶段 3 权威迁移**（按 3.1 → 3.5 顺序，先层生成后拾取）
6. **阶段 1B 上云**
7. **阶段 4 体验完善**
